The backend serves a JSON API under **`/api`**. The web app is its first
consumer: the frontend reverse-proxies `/api/*` to the backend, so the browser
talks to one origin, there is no CORS configuration, and the session cookie flows
naturally.

## Authentication

Signing in creates a server-side session, represented by an **httpOnly cookie**
backed by the Postgres `sessions` table. Browsers use that cookie directly.

Non-cookie clients use a short-lived JWT. First establish a Better Auth session,
then request a token and send it with normal API calls:

```http
Authorization: Bearer <token>
```

| Method | Path              | Authentication      | Purpose                                  |
| ------ | ----------------- | ------------------- | ---------------------------------------- |
| `GET`  | `/api/auth/jwks`  | None                | Public keys for JWT signature validation |
| `GET`  | `/api/auth/token` | Better Auth session | Mint a JWT for normal API calls          |

`/api/auth/token` returns `{"token":"ey…"}`. Tokens contain only standard
claims and expire after 15 minutes. Keep the JWT in memory, refresh it through
the session before expiry, and never send either credential to another origin.
Session revocation prevents a new token from being minted; an issued token stays
valid until it expires.

There is no general-purpose personal-access-token flow. [Identity
OAuth](/reference/identity-oauth/) is separate: its `read:accounts` tokens can
verify a consenting account's minimal public identity, but cannot authenticate
the normal API. The [content webhook](/reference/content-webhook/) has another
separate credential type: its per-user tokens can only publish posts.

### Public gateway origin checks

The public `/api` routes pass through SvelteKit before reaching the backend.
Native and scripted clients should send the destination's origin on mutations,
including bodyless requests such as liking a post:

```http
Authorization: Bearer <token>
Origin: https://your-instance.example
```

An origin contains the scheme, hostname, and non-default port, without a path or
trailing slash. For example, an instance on port 8443 uses
`https://your-instance.example:8443`; the default HTTPS port 443 is omitted.

The gateway checks the origin for `POST`, `PUT`, `PATCH`, and `DELETE` requests
that have no `Content-Type` or use a form content type. A missing or mismatched
origin can return `403 Cross-site POST form submissions are forbidden` before
the backend authenticates the request. A Bearer token does not bypass this check.
Send `Content-Type: application/json` when submitting a JSON request body.

The shipped gateway routes identity OAuth's machine endpoints directly to the
backend rather than through this browser proxy. They accept JSON and
form-encoded bodies without a browser `Origin` header; their confidential-client
or identity-token checks still apply. The browser consent and connection APIs
remain session-protected; see [Identity OAuth](/reference/identity-oauth/).

## Conventions

- **Cursor pagination.** Listing endpoints accept a cursor and return the next
  one. There is no `offset`.
- **Rate limiting.** Writes are throttled per signed-in user, or per IP when
  anonymous; reads are not throttled by the general limiter. A limited request
  gets `429` with `Retry-After`.
- **Backend errors** are JSON, always the same shape — `{"error": "…"}` — with an
  appropriate status code. A request body that fails validation gets `400` and a
  message naming the field, for example
  `{"error":"displayName: Invalid input: expected string, received number"}`. A
  body that is not valid JSON gets `400` too, not `500`.
  Gateway rejections can instead return plain text, including the origin-check
  error above; check the response status and content type before decoding JSON.

`GET /api/posts/random` returns `{"post": …}` or `{"post": null}` when no
posts match. `scope` accepts `global` (the default), `local`, or `for-you`; the
last requires a signed-in reader. `langMode=show|hide` and comma-separated
`langs=en,az` apply to Local and Global, using the same unknown-language and
visibility rules as those feeds. For you is not language-filtered. The endpoint
samples across the full eligible archive rather than a recent page, and returns
`Cache-Control: no-store`.

## Umami Cloud — `/api/site`

These routes are unauthenticated and support the optional
[Umami Cloud integration](/self-hosting/umami/), not the writer dashboard.

| Method | Path                  | Purpose                                     |
| ------ | --------------------- | ------------------------------------------- |
| `GET`  | `/api/site`           | Enabled website ID, or `null` when disabled |
| `GET`  | `/api/site/script.js` | Proxy the fixed Cloud tracker               |
| `POST` | `/api/site/api/send`  | Forward a validated public-page pageview    |

`GET /api/site` returns `{ "websiteId": string | null }`. The script route
returns JavaScript while enabled and `404` while disabled. All three routes
use `Cache-Control: no-store`; the backend caches successful script fetches
in memory for one hour.

Collection accepts `application/json` with `{ "type": "event", "payload": {...} }`.
The payload contains `website` (the configured UUID), `hostname`, `screen`,
`language`, `title`, and `url`; `referrer` is optional. Unknown fields, reader
identifiers, custom event names, and other event types are rejected. The server
removes query strings and fragments and restricts page paths before forwarding.
`X-Umami-Cache`, when present, is forwarded for Cloud session continuity; the
successful Cloud JSON response is returned to the tracker.

Disabled collection or a request carrying `DNT: 1` or `Sec-GPC: 1` returns
`204` without contacting Cloud, subject to rate limits. Cross-site browser
collection requests are refused with `403`. Invalid payloads return `400`,
bodies over **16,384 bytes** return `413`, exhausted request budgets return
`429` with `Retry-After`, and upstream failures return a generic `502`.
See [Rate limits](/reference/rate-limits/#umami-cloud).

Configuration uses the separate [admin-only API](/reference/admin-api/#umami-cloud).

## Media — `/api/uploads`

| Method | Path          | Purpose                                             |
| ------ | ------------- | --------------------------------------------------- |
| `POST` | `/`           | Upload a file                                       |
| `GET`  | `/:file`      | Serve an uploaded file                              |
| `GET`  | `/og/:id.jpg` | A JPEG copy of an upload, for link-preview crawlers |

`/og/:id.jpg` takes the id of an existing upload — whatever its stored format —
and returns it as a JPEG fitted inside 1200×630, generated on first request and
cached on disk. It exists because uploads are stored as WebP, which several
preview crawlers refuse, and because a share image has to be a format every one
of them reads. Unauthenticated by necessity: the caller is a crawler with no
session.

## Remote images — `/api/media/proxy`

`GET /api/media/proxy?url=<encoded-absolute-url>` is an unauthenticated image
endpoint. The web UI uses it for remote avatars, covers, body images, and image
previews so the remote host receives the instance's request, not the reader's.
Stored URLs and ActivityPub payloads are unchanged.

- Only public HTTPS destinations on the default port are fetched. Legacy HTTP
  URLs are upgraded to HTTPS; HTTP-only sources stop displaying.
- PNG, JPEG, GIF, and WebP must match their declared MIME type and raster
  signature. SVG and other active content are refused.
- Transfers are capped at **5 MiB**, **10 seconds total**, and **3 redirects**.
  Each redirect is revalidated; DNS answers are checked and pinned to the socket.
- The process-local cache lasts **1 hour**, with at most **64 entries / 16 MiB**.
  Concurrent misses for one URL share a fetch. There are at most **8** fetches
  globally and **2** per initial origin, per backend process.
- The request limiter allows **240 requests per minute per source IP**. These
  image-proxy limits are source constants, not environment variables.

A successful response contains image bytes, `Cache-Control: public, max-age=3600`,
`X-Content-Type-Options: nosniff`, and
`Cross-Origin-Resource-Policy: same-origin`. Visitor cookies and request headers
are not forwarded upstream; upstream cookies are not returned. Invalid targets
return `400`, unavailable or rejected images `404`, and exhausted request or
concurrency budgets `429`.

## Share cards — `/api/og`

| Method | Path             | Purpose                                                |
| ------ | ---------------- | ------------------------------------------------------ |
| `GET`  | `/posts/:id.jpg` | The card drawn for a post that has no image of its own |

A 1200×630 JPEG carrying the post's title, its author, and the instance —
generated on first request and cached on disk. What a link-preview crawler
fetches as `og:image` when the post has neither a chosen banner nor an image in
its body. Unauthenticated, like the media route above, and built from the same
visibility check a signed-out reader gets: a draft's card is a `404`, exactly
like the draft.

Answers `302` to the instance's brand image when no card can be drawn — a
federated copy of someone else's post, an untitled one, or a title in a script
the bundled font has no glyphs for. A redirect rather than a `404` because an
`og:image` that fails puts no picture on the card at all.

Its own prefix rather than a path under `/api/posts/` so `robots.txt` can allow
it by name — see [Discoverability](/self-hosting/discoverability/#robotstxt).
Nothing but share images belongs here.

## Photos — `/api/photos`

Free-photo search for the editor's banner picker. **Signed in only** — one
provider spends an instance-wide quota.

| Method | Path                         | Purpose                                            |
| ------ | ---------------------------- | -------------------------------------------------- |
| `GET`  | `/providers`                 | Which providers this instance can search, in order |
| `GET`  | `/search?provider=&q=&page=` | Search one provider                                |
| `POST` | `/use`                       | Tell a provider one of its photos was used         |

`/providers` is never empty: Openverse needs no credentials, so it is always
present. Unsplash joins it only when an admin has configured a key. Results from
either provider come back in one shape, carrying the attribution to store with
the post.

`/use` exists for Unsplash's API terms, which require a per-photo call when an
image is actually used; it is a no-op for providers that ask for nothing.
Search carries its own per-user rate limit on top of the general one, because a
`GET` is not covered by the write throttle and both providers are shared
resources.

## Webhooks — `/api/webhooks`

| Method   | Path          | Auth    | Purpose                                 |
| -------- | ------------- | ------- | --------------------------------------- |
| `POST`   | `/content`    | Token   | Publish a document from an external CMS |
| `GET`    | `/tokens`     | Session | Your live publishing tokens             |
| `POST`   | `/tokens`     | Session | Mint one (plaintext returned once)      |
| `DELETE` | `/tokens/:id` | Session | Revoke one                              |

`/content` is the one endpoint that does **not** use the session cookie: it
authenticates with a bearer credential in `X-Webhook-Secret` or
`Authorization: Bearer`, and publishes as that credential's owner. Managing
tokens is an ordinary session-authenticated call, so a token cannot mint or
revoke tokens. Full reference in
[Content webhook](/reference/content-webhook/).

## Reports, instance, setup, SEO

| Method | Path                            | Purpose                                                                 |
| ------ | ------------------------------- | ----------------------------------------------------------------------- |
| `POST` | `/api/reports`                  | Report a post or actor                                                  |
| `GET`  | `/api/instance`                 | Public instance metadata, including visitor card and public information |
| `POST` | `/api/setup`                    | Complete the first-run wizard                                           |
| `POST` | `/api/setup/test-email`         | Send a test email during setup                                          |
| `GET`  | `/api/seo`                      | Indexing flag and verification tokens (the IndexNow key is withheld)    |
| `GET`  | `/api/seo/sitemap-entries`      | Profiles, tags, and public lists for the sitemap, plus the post count   |
| `GET`  | `/api/seo/sitemap-posts?page=N` | One page of published local posts for the sitemap                       |
| `GET`  | `/api/seo/indexnow-key/:key`    | Whether `key` is this instance's IndexNow key                           |

`GET /api/instance` is unauthenticated and powers the site chrome and the
public About, privacy, contact, and status pages. Alongside the name, domain,
federation flag, and visitor card it returns the admin-managed public
information as sanitized HTML (`aboutHtml`, `rulesHtml`, `privacyPolicyHtml`)
plus the contact and status links; each is `null` when the admin has not set
it, in which case the page shows its built-in placeholder or environment
fallback.

`GET /api/instance/tls-check?domain=…` is **internal only**: Caddy calls the
backend directly before issuing a certificate. Both the public Caddy route and
the frontend API proxy return `404` for it. A custom reverse proxy must preserve
that boundary rather than publishing the backend directly.

`GET /.well-known/security.txt` publishes the project's vulnerability-reporting
contact, an expiry 180 days ahead, and the preferred language. It is served as
plain text with a one-day cache and bypasses federation routing and the bot
challenge.

Administrative endpoints are documented separately in
[Admin API](/reference/admin-api/).
