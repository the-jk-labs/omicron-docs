
## Security-hardening upgrade

The remote-image proxy, browser policy, and Caddy admin socket must ship
**together**. Do not deploy just the frontend: it will request an image endpoint
the old backend does not provide. Do not reload only the Caddyfile: the old
backend still expects the removed admin TCP listener.

1. Before upgrading, create a backup and verify the new snapshot exists:

   ```bash
   docker compose exec backup backup-now
   docker compose exec backup restic snapshots
   ```

   Stop if the backup fails or the snapshot is missing. Keep an off-host copy
   and a tested restore procedure; see [Backups](/self-hosting/backups/).

2. Remove a legacy `CADDY_ADMIN_URL=http://caddy:2019` override from `.env`, if
   present. The bundled stack now uses `/run/caddy-admin/admin.sock`; a nonempty
   custom URL takes precedence and would keep the toggle pointed at the old port.

3. Pull the release containing the change and recreate the three services:

   ```bash
   git pull
   docker compose up -d --build --force-recreate backend frontend caddy
   ```

   Compose creates the `caddy_admin` volume and mounts it only in Caddy and the
   backend. Do not delete existing database, upload, secret, or certificate volumes.
   Podman Compose users can use the equivalent commands.

4. Check sign-in, remote avatars and article images, and the scraper-protection
   toggle in both directions. Confirm `/.well-known/security.txt` is public and
   `/api/instance/tls-check?domain=your-domain` returns `404` through the public
   entrypoint. Check Caddy and backend logs for socket or config-reload errors.

No schema migration or content backfill is required by these hardening changes.
HTTP-only remote images may stop displaying: the proxy requires HTTPS. Style
attributes are limited to fixed declaration hashes; custom server-rendered
inline styles may need to move into a stylesheet. DNS/mail policy, DNSSEC, and
CAA are separate operator work. HSTS preload remains off unless the owner opts
in after checking the whole domain tree; see [Security](/self-hosting/security/#domain-and-mail-hardening).

## What happens

- **Migrations run automatically** on backend startup and are idempotent — a
  no-op when the schema is already current.
- A rebuild recreates the **containers** but never the **volumes**, so your data,
  secrets, and TLS certificates are preserved.
- `image prune`/`builder prune` drop the previous build's now-untagged image
  layers and build cache, so a `--build` upgrade never leaves disk usage
  creeping up. Both only remove untagged, unused layers — never a named
  volume — so this is safe to run every time.
- The app version is logged on boot and exposed at `GET /version`.

<Callout type="tip" title="Back up first">
  Take a backup before any significant upgrade — `docker compose exec backup backup-now` takes a minute and turns a bad
  release into an inconvenience. See [Backups and restore](/self-hosting/backups/).
</Callout>

## Migration policy

Upgrades must never break a running instance, so schema changes are **additive
only** within a version:

1. **Add** new columns and tables (nullable or with defaults) and migrate data.
2. Ship code that works with **both** the old and the new shape.
3. **Remove** old columns only in a later major release.

Migrations are versioned SQL in `apps/backend/drizzle/`, replayed at runtime by
`src/db/migrate.ts`. `drizzle-kit` is **not** required inside the container.

## Site traffic dashboard

The traffic feature adds the `traffic_buckets` table through
`0044_daily_gateway.sql`; `0045_cookieless_traffic.sql` then removes the unused
visitor/visit sketch columns, preserving pageview counters. Back up and verify
the snapshot **before** deploying the release containing it:

```bash
docker compose exec backup backup-now
docker compose exec backup restic snapshots
```

Stop if either command fails or the new snapshot is missing. Then pull the
release and rebuild both apps using the normal upgrade commands. Migrations
run on backend startup. No Caddy configuration change or extra service is
required for basic traffic reports.

After deployment, collection stays **off** until an admin enables it in
**Admin → Traffic**. It does not import earlier traffic or alter the writer
dashboard's existing post-read counts. Update the instance privacy policy and
arrange any required consent before enabling it; see [Site traffic](/self-hosting/traffic/).

Country reports additionally need the optional `TRAFFIC_GEOIP_PATH`, a local
MMDB directory mounted read-only into the backend, and backend recreation.
Follow the [country setup](/self-hosting/traffic/#optional-country-lookup)
instead of exposing a database or lookup endpoint to the public internet.

## One-time step: IP access rules

The IP access-rule UI needs a managed insertion marker in the shipped
`Caddyfile`. Existing deployments must pick up that file in both Caddy and the
backend; `restart` alone can leave a replaced bind-mounted file pointing at its
old contents.

1. Create a backup and verify its snapshot before upgrading:

   ```bash
   docker compose exec backup backup-now
   docker compose exec backup restic snapshots
   ```

   Stop if either command fails or the new snapshot is missing.

2. Pull the release and recreate the affected services:

   ```bash
   git pull
   docker compose up -d --build --force-recreate backend frontend caddy backup
   ```

   The backup service also mounts the Caddyfile, so recreate it to keep future
   configuration backups current. Never delete named volumes. Podman Compose
   users can use the equivalent commands.

3. Open **Admin → Security → IP access rules**. Preview a draft against a test
   address and `/search`, then against `/admin`; the latter must report an
   exempt path. A preview does not create a live block. Confirm normal sign-in,
   public reading, feeds, and API access still work.

This feature adds no schema migration or environment variable, and starts with
no custom rules. A missing-marker error means the backend is still reading an
older Caddyfile. Stored rules are re-applied after Caddy becomes reachable on
startup; the short startup gap is fail-open, not a durable network firewall.

## One-time step: the AI-scraper-shield release

That release changed the bundled **Caddyfile** to open an internal admin API the
scraper-shield toggle uses. Caddy only reads that file at startup, and a plain
`up -d` does not recreate an unchanged service — so recreate the containers once:

```bash
docker compose up -d --build --force-recreate
```

This recreates **containers**, never volumes, so all data and certificates
survive. If you skip it nothing breaks: the instance runs normally and protection
stays off (the default); you simply cannot switch it on in **Admin → Security**
until Caddy has been recreated. After that release, normal `up -d` upgrades
resume.

<Callout type="note">
  The same trick applies any time a release changes `Caddyfile` or another file a service only reads at startup. Release
  notes will say so explicitly.
</Callout>

## One-time step: the Redis 8 release

That release moved the bundled Redis from 7.4 to 8. Redis 7.4 is offered only
under RSALv2 and SSPLv1, neither of which is an open-source licence; Redis 8
restores AGPLv3 as an option, matching Omicron's own licence.

**Nothing is required of you.** Redis 8 reads the files 7.4 wrote, so a normal
`git pull && docker compose up -d --build` upgrades it in place. The backend logs
a few seconds of `ENOTFOUND redis` while the container is replaced, then
reconnects on its own.

<Callout type="warning" title="This step cannot be rolled back">
Redis 8 writes its snapshot in a format 7.4 cannot read. Once you have upgraded,
checking out an older tag leaves the `redis` container crash-looping with
`Can't handle RDB format version 14`. Clear the volume to go back:

```bash
docker compose down
docker volume rm omicron_redis_data
docker compose up -d --build
```

Only regenerable state lives there — rate-limit counters, queued jobs, and
federation activities not yet delivered. No posts, accounts, or uploads. Activities
still queued are lost, so remote instances may never receive them.

</Callout>

## One-time step: the scraper-shield fixes release

That release changed the bundled **Caddyfile** again, so it needs the same
recreate as the original shield release:

```bash
git pull && docker compose up -d --build --force-recreate
```

A plain `up -d` leaves Caddy on the old file and the fixes silently do not apply.
What you get once it is recreated:

- The challenge page no longer hangs on "Calculating…" until the reader
  refreshes.
- Page loads no longer fail with a 500 when the reader's IP arrives from a
  private network.
- The challenge signing key is generated once into the `secrets` volume, so
  restarts and upgrades stop re-challenging readers who already solved one.

Containers are recreated, never volumes, so data and certificates survive. If
the shield is on, it drops for a few seconds while Caddy restarts and the backend
re-applies it — readers see the site unprotected, not broken.

The release also adds `ANUBIS_REDIRECT_DOMAINS`. Nothing breaks if you leave it
unset, but a public instance should set it — see
[Environment variables](/reference/environment/).

## One-time step: the challenge status-code release

The release that made a challenge answer `503` instead of `200` touches two
files the containers only read at startup — `botPolicy.yaml` and the
`Caddyfile` — so it needs the same recreate:

```bash
git pull && docker compose up -d --build --force-recreate
```

A plain `up -d` leaves the challenge answering `200` with no `Retry-After`.
Nothing breaks either way; the point of the change is that automated clients —
search engines, uptime monitors, link checkers — stop being told a refusal
succeeded. See
[what a challenged request gets back](/self-hosting/admin-panel/#what-a-challenged-request-gets-back).

If you only edited `botPolicy.yaml` yourself and want it picked up without
recreating anything else, `docker compose restart anubis` is enough.

## Identity OAuth

The identity OAuth release adds four tables (`oauth_apps`, `oauth_requests`,
`oauth_codes`, and `oauth_tokens`) through migration `0043_gorgeous_shape`.
Migrations run automatically on backend startup. Existing usernames, posts,
sessions, and the NodeInfo software name remain unchanged. No new environment
variables are required.

1. Before updating, take a backup and verify the new snapshot exists:

   ```bash
   docker compose exec backup backup-now
   docker compose exec backup restic snapshots
   ```

   Stop if the backup fails or the snapshot is missing.

2. Pull the release and recreate all services that build the new application or
   mount its updated proxy and bot-policy files:

   ```bash
   git pull --ff-only
   docker compose up -d --build --force-recreate backend frontend caddy anubis backup
   ```

   This refreshes `Caddyfile` in the backend, Caddy, and backup containers, and
   `botPolicy.yaml` in Anubis and backup. A plain `restart` can leave an old
   bind-mounted file in place. Preserve every named volume. Podman Compose users
   can use the equivalent commands.

3. Validate the proxy configuration and check service status:

   ```bash
   docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
   docker compose ps
   ```

   Confirm `/.well-known/oauth-authorization-server` returns JSON with the
   instance's canonical issuer, `GET /api/v1/accounts/verify_credentials` without
   a token returns `401` rather than a bot challenge, and NodeInfo still
   advertises `omicron`. Check normal sign-in and reading. A complete third-party
   sign-in also requires a supported client; see
   [Identity OAuth](/reference/identity-oauth/).

The new Caddy machine-endpoint routes are required for form-encoded OAuth
clients; do not fix origin-check failures by disabling browser CSRF protections.
The backend re-applies saved scraper-shield and access-rule settings when Caddy
is reachable after startup. FediDB still needs its own Omicron support change;
upgrading the instance alone does not remove that service's software allowlist.

## Rolling back

Check out the previous tag and rebuild:

```bash
git checkout <previous-tag>
docker compose up -d --build
```

<Callout type="warning" title="Rollbacks are not always safe">
Migrations run forward automatically; they are not reversed on downgrade. Because
schema changes are additive within a version, rolling back a **patch** release is
usually fine — the old code ignores the new columns. Rolling back across a
**major** release, where columns may have been dropped, is not. Restore from a
backup instead.

A release that raises the version of a bundled service can also block a
downgrade, because the newer service may leave data the older one refuses to
read. Rolling back past the Redis 8 release is the current example — see
[above](#one-time-step-the-redis-8-release). Release notes call these out.

</Callout>

## Never run this on a live instance

```bash
docker compose down -v   # deletes every volume: database, uploads, secrets, certs
```

`down` (without `-v`) is safe — it stops containers and leaves your data alone.
